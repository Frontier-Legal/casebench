`casebench.profile/1.0`. A data provider's description of its API, in YAML. A profile is a saved answer to `casebench corpus add`: its `options` are exactly what that command would write. Users connect it with `casebench corpus add profile FILE`, `casebench init --profile FILE`, or the workbench's Jurisdictions page. Each makes one live search with `probe` and one fetch with the user's key before anything is written.

## Example

```yaml title="acme-legal.yaml"
format: casebench.profile/1.0
name: Example Legal Data
jurisdictions: [GB]
docs: https://example.com/docs
terms: https://example.com/terms
key_env: EXAMPLE_API_KEY
metered: search
maintainer: Example Legal Data <data@example.com>
connector: http
options:
  base_url: https://api.example.com/v1
  headers:
    Authorization: Bearer ${EXAMPLE_API_KEY}
  search_path: /search
  search_params:
    q: "{text}"
  search_ids: $.results[*].id
  fetch_path: /documents/{id}
  fields:
    id: $.id
    jurisdiction: $.jurisdiction
    court: $.court.name
    date: $.decided_on
    text: $.body
probe: unfair dismissal
```

`casebench validate acme-legal.yaml` accepts this profile.

## Bundling a profile with Casebench

A profile can ship inside Casebench, listed by name in `casebench init`, and then be named by its id instead of a file. Casebench 0.5.1 bundles none. Every provider meets the same bar: a `maintainer` who answers issues, a recorded search and fetch the provider may redistribute, and a passing offline test. See [Write a plugin or a profile](/integrations/extend/plugins/).
